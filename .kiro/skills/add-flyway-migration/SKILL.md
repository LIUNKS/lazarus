# Add a Flyway migration

## Rules that never change
- Migrations live in `db/migrations/V<N>__<description>.sql`. `<N>` is the next integer after the highest existing one.
- An existing migration is immutable, because Flyway validates its checksum. That includes `V2__seed_sample_corpses.sql`, which is generated by `db/seed/generate-seed.ts`. To change anything, add a new migration.
- No secrets in the file or in `db/flyway.conf`. Credentials come from the environment (`FLYWAY_*`), loaded by `pnpm db:migrate` through `dotenv-cli`.
- Connect through the direct connection or the Session Pooler on port 5432. Never use the Transaction Pooler (6543): Flyway needs session advisory locks.

## Writing the SQL
1. Use `uuid` primary keys with `gen_random_uuid()` and `timestamptz` timestamps.
2. Every new table: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` in the same migration, plus its policies.
3. Policies use `(select auth.uid())`, not `auth.uid()`, so the planner can cache the value.
4. Tables without a `user_id` (like `curses`, `seance_specs`, `reincarnations`) get their policies through the parent corpse:
   - public read when the parent has `is_sample = true`
   - owner access when the parent has `user_id = (select auth.uid())`
5. For `corpses`, owner `INSERT` and `UPDATE` must require `is_sample = false` in `WITH CHECK`. Anonymous users never get write access, and `user_id IS NULL` is not a public marker.
6. Index every new foreign key column (`corpse_id` style) and `corpses.user_id`.
7. Changing a CHECK constraint: `DROP CONSTRAINT` then `ADD CONSTRAINT` with the full new list. Keep the allowed values consistent with `.kiro/steering/database-and-exorcism.md`, and update that file in the same change.
8. Trigger functions that touch `auth.users` data must be `SECURITY DEFINER` with a fixed `search_path`.
9. The service role key bypasses RLS and is used only in server-side Route Handlers. Never grant a policy to rely on it.

## Verify
1. `pnpm db:migrate` applies the migration to the configured database (Flyway CLI must be on PATH).
2. `pnpm test:db` runs the schema and seed tests. Update `db/tests/schema.test.ts` when you add a constraint, table, or policy.
3. Check the policies by reasoning about three roles: `anon`, an authenticated owner, and an authenticated user who is not the owner. Each must see exactly what the steering file says.
4. Add new environment variables to `.env.example` with placeholder values only.

## Report
List the file name, what changed, which commands you ran with their exit codes, and which you could not run.
