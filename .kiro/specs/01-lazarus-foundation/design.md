# Design Document

## Overview

The Foundation delivers three things: the pnpm + Turborepo monorepo scaffolding, the Flyway-managed Supabase schema with RLS, and three executable sample corpses seeded by migration. A Vitest Verification_Suite proves the database behavior against a real Postgres.

Key decisions:

1. **Local Postgres for verification.** Tests never touch the Supabase project in `.env`. `db/local/docker-compose.yml` starts `postgres:17` on port 54329. The suite reads one variable, `TEST_DATABASE_URL`, and skips every database test with a message naming it when it is unset (Requirement 16.7).
2. **Supabase stub.** Plain Postgres has no `auth` schema, no `anon`/`authenticated`/`service_role` roles, and no Supabase default privileges. `db/harness/supabase-stub.sql` (idempotent) creates them, including `auth.users`, `auth.uid()` (reads `request.jwt.claim.sub`), and `ALTER DEFAULT PRIVILEGES ... GRANT ALL ... TO anon, authenticated, service_role`. The default privileges matter: they reproduce the real Supabase exposure that V1 must revoke (Requirements 12.3 to 12.5, 15.3). The stub is applied to the test database and to every scratch database before Flyway runs. Real Supabase already has all of it, so V1 contains no stub code.
3. **Generated seed.** `V2__seed_sample_corpses.sql` is generated by `db/seed/generate-seed.ts` from authored sources in `db/seed/<sample>/`. The generator computes `code_hash`, resolves curse line numbers from text markers, runs the `pbt_test_code` through the `db/harness/` runner, and records `pbt_passed`, `total_runs`, and `execution_time_ms` as literals. The generated file is committed and never edited by hand (Flyway checksums it).
4. **Harness runner.** `db/harness/pbt-runner.ts` implements the Test_Code_Contract from `database-and-exorcism.md` with `node:vm` and `fast-check`. It is a test and seed tool only; `packages/pbt-verifier` is the runtime implementation built in spec 03.
5. **Scripts in TypeScript.** Node 24 strips types natively, so `scripts/*.ts` and `db/**/*.ts` run with plain `node` and are covered by `tsc --noEmit` and ESLint (`erasableSyntaxOnly`, `allowImportingTsExtensions`).
6. **TypeScript 6.** The root declares `typescript@^6`. `typescript-eslint` 8.x supports TypeScript `<6.1`, and the later `pbt-verifier` needs the importable compiler API that 7.x lacks.

## Architecture

```text
lazarus/
├── package.json, pnpm-workspace.yaml, turbo.json, .npmrc, .gitignore
├── tsconfig.base.json, tsconfig.json, eslint.config.mjs, vitest.config.ts
├── scripts/
│   ├── db-migrate.ts        # Migration_Runner checks, then flyway
│   ├── workspace-task.ts    # runs turbo for build/test/lint, handles the empty-workspace case
│   └── test-db.ts           # up | down | migrate helpers for the local test database
├── db/
│   ├── flyway.conf
│   ├── migrations/          # V1__create_lazarus_schema.sql, V2__seed_sample_corpses.sql
│   ├── local/docker-compose.yml
│   ├── harness/             # supabase-stub.sql, pbt-runner.ts, deep-equivalent.ts, typecheck.ts
│   ├── seed/                # generate-seed.ts and one folder per sample
│   └── tests/               # Verification_Suite (*.test.ts) and support/
└── .env.example
```

### Migration_Runner flow

`pnpm db:migrate` → `dotenv -e .env -- node scripts/db-migrate.ts`. The script checks, in order: `FLYWAY_URL`/`FLYWAY_USER`/`FLYWAY_PASSWORD` present and non-blank (names only in the error), port in `FLYWAY_URL` is not 6543, `flyway` resolves on `PATH`. Then it spawns `flyway -configFiles=db/flyway.conf migrate` once with inherited stdio and exits with Flyway's code. It never prints the password.

### Workspace tasks

`turbo run <task>` errors when no package defines the task. `scripts/workspace-task.ts <task>` lists workspace packages that define the script (via `pnpm ls -r --json`-free logic: it reads `packages/*/package.json` and `apps/*/package.json`). If none define it, it exits 0 after the Foundation's own checks; otherwise it runs `turbo run <task>`, which prints each failing package.

### Schema (V1)

Tables as in `database-and-exorcism.md`. Non-obvious choices:

- `corpses.status` defaults to `'INFECTED'`; `is_sample`, `source_language`, `status`, `severity`, `curse_type` are `NOT NULL`.
- Child policies use `EXISTS` against `corpses`; each command gets its own policy, and every write policy names `TO authenticated`.
- Grants: `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, then `anon` gets `SELECT` on all five tables (profiles has no anon policy, so it returns zero rows, Requirement 15.4), `authenticated` gets full DML on the four data tables and `SELECT, UPDATE` on `profiles`.
- `public.handle_new_user()` is `SECURITY DEFINER`, `SET search_path = ''`, uses `ON CONFLICT (id) DO NOTHING`, and has `EXECUTE` revoked from `PUBLIC`, `anon`, `authenticated`.
- `REVOKE ALL ON public.flyway_schema_history FROM PUBLIC, anon, authenticated`.

### Verification_Suite

Role switching inside a transaction: `SET LOCAL ROLE anon|authenticated` plus `SELECT set_config('request.jwt.claim.sub', $1, true)`. Support helpers create two or more users (`auth.users` inserts, which fire the profile trigger), create fixture corpses and child rows through the owner role, record every id, and delete them in `afterAll` (also on failure). Migration tests (Requirements 7 and 8) create a scratch database per test, apply the stub, run Flyway through `child_process`, and drop the database afterward. Flyway receives its connection through `FLYWAY_URL`, `FLYWAY_USER`, and `FLYWAY_PASSWORD` derived from `TEST_DATABASE_URL`.

Test names follow `R<requirement>.<criterion> <description>` so Requirement 16.2 can be checked mechanically.

Static and seed checks (Requirements 1 to 5, 7, 17 to 20) use `acorn` (ES3 and ES5 grammars), a small scope analysis for the curse markers, `node:vm` for purity and determinism, and the TypeScript compiler API for the strict compile of `modern_code`.

## Sample corpses

| Sample | `source_language` | Entry function | Curses |
|---|---|---|---|
| Invoice totals | `es3` | `computeInvoiceTotal` | `GLOBAL_POLLUTION` (top-level implicit global, outside the entry function), `VAR_HOISTING`, `IMPLICIT_COERCION` |
| Query string parser | `es5-jquery` | `parseQueryString` | `PROTOTYPE_POLLUTION` (variable-key assignment), `VAR_HOISTING`, `IMPLICIT_COERCION` |
| Batch calculator | `legacy-node` | `calculateBatch` | `CALLBACK_HELL` (three nested synchronous callbacks), `EVAL_INJECTION` (`new Function` over a whitelisted operator), `VAR_HOISTING` |

The implicit-global assignment sits at the top level because Requirement 17.7 forbids the entry function from writing global state. Entry functions are self-contained: helpers are nested inside them.

## Error handling

The runner and suite follow the requirements' failure rules: nothing is printed that contains `FLYWAY_PASSWORD`; a missing prerequisite exits non-zero with a message that names it; database tests report skipped (variables unset) or failed (connection did not succeed within 10 seconds).

## Testing strategy

The Verification_Suite is the deliverable. It runs with `pnpm test` (skips database tests when `TEST_DATABASE_URL` is unset) and with `pnpm test:db`, which starts the Docker database, applies the stub, migrates, and runs the suite.
